# Loom autonomous loop — operating instructions

**Purpose.** Drive `docs/Build Plan V2/Access Control and Workflow Service Tracker.md` to completion,
autonomously, without violating the guardrails below. This file is the authoritative brief for each loop
iteration; read it fully at the start of every iteration before doing anything else.

**Last updated:** 2026-08-17, at commit `47fca1a8`.

---

## 1. Hard rules — never violate these, no exceptions

These exist because each one was learned from a real failure in this project. Violating one is worse
than making no progress at all.

### 1.1 Community JSON is locked and requires per-instance human approval

- `docs/references/communities/*.jsonc` are **read-only on disk** (`chmod 444` on the VM, read-only
  attribute on the Windows checkout). This is deliberate.
- **Never** write, edit, or apply content to these files directly — not with Write, not with Edit, not
  with a shell redirect, not via a dispatched agent.
- Community JSON content may **only** be generated by dispatching the authoring Skill
  (`bash data/call_skill_authoring_agent.sh <target-doc> [label]`), which runs a zero-repo-access Codex
  agent that returns text only.
- Generating it is **not** sufficient to apply it. The apply step requires the user's **fresh, explicit,
  per-instance approval** — show the full diff/output, wait for a real answer, and only then:
  `unlock the one file → apply → verify (validator) → immediately re-lock (chmod 444)`.
  Never leave a community JSON file writable outside that narrow window.
- A broad earlier authorization ("migrate all the communities…") does **not** substitute for per-file
  approval. This exact mistake was made and reverted on 2026-08-17.

### 1.2 The lock does not survive git operations — re-apply it

`git reset --hard` / `checkout` / `pull` silently restores write permissions, because file modes are not
git-tracked. The VM is reset after nearly every dispatch. **After every VM sync, re-run:**

```bash
ssh loom-vm 'chmod 444 ~/Loom/docs/references/communities/*.jsonc'
```

Verify with a real write attempt (expect `Permission denied`), not an `ls -l` glance.

### 1.3 Escalate to the user — stop and ask — for any of these

- Any change to a **JSON specification** (community fixtures, spec-version.json semantics).
- Any **MAJOR architecture change** (new service, new package boundary, replacing a core mechanism,
  changing how auth or the engine is fundamentally structured).
- Anything touching **Hyper-V** — explicitly and permanently deferred by user decision. Never disable it,
  never "just try" it.
- Destructive/irreversible operations on infrastructure beyond a routine, already-proven recovery.

**Small** architecture changes (modifying an existing API, expanding an existing API, adding a seam that
mirrors an already-approved pattern) may proceed autonomously — but **must be surfaced to the user at
the start of the next loop iteration** and confirmed before being treated as settled.

### 1.4 Never trust a dispatched agent's self-report

STATUS.md is a claim, not a result. For **every** dispatch, independently:
1. Read the actual `git show <sha>` diff — all of it.
2. Run `dart analyze` / `flutter analyze` yourself.
3. Run the relevant test suites yourself on the VM, and compare failures **by exact test name** against
   the known-pre-existing set (see §4).
4. Only then reconcile git and write the tracker closeout.

Dispatch sandboxes frequently cannot bind localhost sockets (`Failed to create server socket … errno = 1`)
— a recurring, known limitation. When a dispatch says it could not run tests, that is honest, not a
failure; you run them instead.

### 1.5 Git safety

- **Push a verified commit to origin before** writing its closeout doc or running any `git reset` on that
  repo. Never `git reset --hard` a repo that may hold an unpushed dispatch commit.
- Dispatches sometimes land on a stray branch. Always check `git branch --show-current` and confirm a
  clean fast-forward/ancestor relationship before merging.
- Local↔VM reconciliation: add a temporary remote, fetch, verify ancestry, fast-forward, push, remove the
  temp remote:
  ```bash
  git remote add loom-vm-direct-loom loom-vm:Loom
  git fetch loom-vm-direct-loom main
  git merge-base --is-ancestor HEAD loom-vm-direct-loom/main   # must succeed
  git merge --ff-only loom-vm-direct-loom/main && git push origin main
  git remote remove loom-vm-direct-loom
  ```

### 1.6 Every implementation ticket must exclude the spec/community docs

Every dispatched ticket's "Do not do" section must contain:
`Do not edit any file under docs/references/{reference,guide,archetypes,communities}/`.

### 1.7 Application code changes go through the Implementation Agent

Don't hand-edit application code. Write a ticket, dispatch it, verify it. Docs, tracker rows, and Skill
definition files are the exception — those are edited directly.

## 2. Operational mechanics

### Dispatching an implementation ticket

```bash
scp <ticket>.md loom-vm:~/Loom/data/
ssh loom-vm '. ~/.loom-env.sh && cd ~/Loom && \
  CODEX_IMPLEMENTATION_PROFILE=gpt5_6_sol_xhigh \
  nohup bash data/call_implementation_agent.sh data/<ticket>.md --fresh > ~/<label>.log 2>&1 &'
```

- **Always set `CODEX_IMPLEMENTATION_PROFILE=gpt5_6_sol_xhigh`.** The default profile
  (`gpt5_3_spark`) has a separate, frequently-exhausted quota — omitting this has already wasted a
  dispatch.
- **Always pass `--fresh`** so it starts a clean session rather than resuming a prior one.
- Then arm a persistent monitor:
  ```
  ssh loom-vm 'tail -F -n +1 ~/<label>.log' | grep --line-buffered -E \
    "^codex exec exited with status|hit your usage limit|panic:|FAILED \(|^fatal:"
  ```

### Dispatching the authoring Skill (community JSON only)

```bash
ssh loom-vm '. ~/.loom-env.sh && cd ~/Loom && \
  nohup bash data/call_skill_authoring_agent.sh data/<brief>.md <label> > ~/<label>.log 2>&1 &'
```
Default profile is already correct for this script. Output lands at
`~/Loom/.codex-logs/skill-authoring/<label>/final_answer.md`. Monitor for `turn.completed`/`turn.failed`.
**Remember §1.1: its output still needs per-instance approval before it touches a file.**

### Running the validator yourself (mandatory gate for any JSON change)

```bash
ssh loom-vm '. ~/.loom-env.sh && cd ~/Loom && \
  dart run app/packages/tooling/loom_ux_judges/bin/community_package_validator.dart --package <file>'
```
Always compare against the **pre-change** run of the same file. Parity (same errors/warnings) is the bar;
a fixture that already had pre-existing findings is not a regression.

### Writing a good ticket

Ground every claim in code you have read yourself. State the trap(s) explicitly. Give exact file paths
and function names. Include: `## Context`, `## Scope`, `## Required verification`, `## Do not do`,
`## Git safety reminder`, `## Commit`, `## Required response format`. Never hand the agent expected
values you have not independently derived.

## 4. Known-pre-existing test failures — do not "fix", do not count as regressions

The `loom_communities_app_shell` Flutter suite has had exactly these 3 failures, by name, in every run
this entire effort. They are precisely diagnosed and deliberately deprioritized:

1. `organizer creates an event and one pending response per member`
2. `custom event creation and recurring generation seed custom response rows`
3. `missing custom response row keeps organizer event-level actions visible`

Any *other* failure is a real regression from the change under test. `flutter analyze` on the app shell
has 8 pre-existing informational lints — same rule.

## 7. Each loop iteration

1. Read this file. Check `git log --oneline -3` on both local and VM; re-apply the community-JSON lock
   (§1.2) if the VM was reset.
2. **Surface to the user**, at the top of your response: any small-architecture decision made since the
   last iteration that has not yet been confirmed, and anything newly discovered that is blocked on them.
3. Check for in-flight dispatches before starting new ones (`pgrep -af codex` on the VM).
4. Advance the highest-priority unblocked item in §5.
5. Verify independently (§1.4), reconcile git (§1.5), write the tracker closeout row citing the real
   evidence, push.
6. Update this file's §3/§5 when the state materially changes.

**Stop the loop and ask** when: a §1.3 escalation is hit, the priority queue is empty of unblocked work,
or the same failure recurs twice with no new information — in that case report the precise diagnosis
rather than retrying a third time.
